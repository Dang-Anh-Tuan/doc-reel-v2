# P4 · Nhận file từ inbox (UC1)

## Quyết định chính
- `InboxWriter` là cổng ghi duy nhất: ghi `*.json.part` rồi `Files.move(ATOMIC_MOVE)` sang `{channel}-{yyyyMMdd'T'HHmmss}-{ref}.json`. Channel/ref được lọc về `[A-Za-z0-9_-]` để không bị path traversal.
- `InboxWatcher` quét mỗi 10s (`docreel.inbox.poll-interval`), chỉ đọc `*.json`, nên không bao giờ thấy file ghi dở.
- Đọc qua `ScriptParser` (P1), gọi `JobService.submit(script, origin)` (P2) NGOÀI transaction.
- Origin: lấy từ JSON nếu có (để báo kết quả về chat), nếu không dùng `inbox` + tên file.
- Kết quả: tạo job → `work/{jobId}/input.json`; JSON sai → `failed/` + `<tên>.error.txt` (mỗi dòng `path: message`); trùng khóa → `duplicate/`.
- Chuyển sang `done/` khi job xong là việc của pipeline (P5), watcher không biết vòng đời job.
- Lỗi hạ tầng (DB mất kết nối) → giữ file trong inbox, lần quét sau thử lại, không đẩy nhầm vào `failed/`.

## Trade-off
- Polling đơn giản, chạy được trên mọi hệ file, đổi lại trễ tối đa 10s (WatchService dễ mất sự kiện trên Windows/network drive).
- Di chuyển file sau khi submit: nếu crash giữa hai bước, lần quét sau gặp lại file → submit trả DUPLICATE → vào `duplicate/`. Không tạo job đôi nhờ idempotency key.
- `scan()` là `synchronized` để scheduler và test/tay gọi không đụng nhau.

## 3 câu hỏi phỏng vấn
1. Làm sao tránh đọc file đang ghi dở? -> Ghi `.part` rồi rename nguyên tử (cùng volume), watcher chỉ nhìn `*.json`.
2. Crash giữa submit và move file thì sao? -> Submit idempotent (unique key) nên chạy lại chỉ ra DUPLICATE; không mất, không nhân đôi job.
3. Vì sao không dùng `WatchService`? -> Không đảm bảo trên Windows/mount mạng, có thể rớt sự kiện; polling 10s + lọc theo trạng thái thư mục là đủ và dễ test bằng `@TempDir`.
