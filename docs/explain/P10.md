# P10 · Upload YouTube (UC1)

## Quyết định chính
- Dùng `java.net.http.HttpClient` + Jackson sẵn có, không thêm thư viện Google (tránh kéo cả SDK, dễ mock bằng WireMock).
- Upload resumable 2 bước: POST khởi tạo (metadata JSON, `privacyStatus=private`) lấy `Location`, rồi PUT cả file.
- Mọi request qua một hàm `send`: 401 → làm mới access token đúng 1 lần rồi thử lại; 5xx / lỗi mạng → thử lại tối đa `maxAttempts` (backoff tăng dần); 4xx khác → lỗi ngay.
- `YouTubeMetadata` là logic thuần: tiêu đề cắt ≤ 100 code point, mô tả có `sources`, tag theo `track`.
- Playlist theo `track`: duyệt `playlists.list?mine=true` (có phân trang), không thấy thì tạo private; cache id trong bộ nhớ.
- `OAuthTokenStore`: refresh token mã hóa AES-256-GCM, khóa = SHA-256(passphrase lấy từ cấu hình/biến môi trường). Sai khóa hoặc file bị sửa → coi như chưa cấp quyền.
- `--youtube-auth`: mở cổng loopback, in URL đồng ý ra log, nhận `code`, đổi lấy refresh token.
- `YouTubeUploadStep` idempotent qua `work/{jobId}/youtube-id.txt`; xong thì phát `VideoUploadedEvent` cho phase sau (bảng `video`).

## Trade-off
- Thử lại cả request PUT từ đầu thay vì nối tiếp phiên (Content-Range): đơn giản, đổi lại tốn băng thông khi file lớn (Shorts < 100 MB nên chấp nhận).
- Khóa từ SHA-256 chứ không PBKDF2: passphrase là secret ngẫu nhiên của máy, không phải mật khẩu người dùng.
- Quota: videos.insert ≈ 1600 unit, playlistItems/playlists.insert 50 unit; 10.000/ngày → ~5 video/ngày. Cần biết khi chạy hàng loạt.

## 3 câu hỏi phỏng vấn
1. Vì sao 401 chỉ làm mới token một lần? Tránh vòng lặp vô hạn khi refresh token bị thu hồi; lần 2 vẫn 401 là lỗi cấp quyền, phải báo người dùng chạy lại `--youtube-auth`.
2. Test retry 5xx mà không chờ thật? Backoff cấu hình được (`Duration.ZERO` trong test) và WireMock scenario đổi trạng thái sau lần lỗi đầu.
3. Retry sau khi upload xong nhưng chưa đổi state có tạo video trùng không? Không: id ghi ra file trước khi đổi state, lần chạy lại thấy file thì bỏ qua.
